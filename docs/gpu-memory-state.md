# B300 GPU memory state (opt-in)

The B300 Rust exporter can replace the separate Python BMC polling process once a site has verified equivalence. The default configuration is unchanged. This feature performs read-only GETs and cannot clear ECC counters, reset GPUs, or modify BMCs.

For the existing IDC-local target entries, opt in with "gpu_memory_state": true (only the B300 profile supports it). Use one alias for each BMC address. Set REDFISH_EXPORTER_GPU_MEMORY_STATE_FILE to an absolute path in an existing writable private directory; mount the directory rather than a single state file because updates use atomic replacement. Baseline files contain GPU identity and must have mode 0600 on Unix. REDFISH_EXPORTER_GPU_MEMORY_INTERVAL_SECS defaults to 300 and accepts 300–480. The ordinary hardware scrape cadence does not need to change.

The background schedule is staggered, with at most two concurrent memory rounds and a 45-second / 35-GET maximum per round. It reuses the existing per-BMC mutex, global GET semaphore and HTTP 403 backoff; expired or late rounds stay incomplete rather than starting an unbounded retry. Main /metrics uses the same cached GPU processor inventory and memory counter measurements, so it does not repeat those GETs for an opted-in target. Other hardware collection remains on its existing path.

The snapshot reads Pending and Failed flags from the GPU Memory members, uses matching Processor UUID and serial to distinguish replacements, and reads a reset marker only from the advertised same-slot path. An HGX_MemoryMetrics_0 entry needs a valid native timestamp (age less than 900 seconds and at most 60 seconds ahead) and a new source observation. Missing, invalid, stale, repeated, or old-slot samples fall back to the matching direct MemoryMetrics resource within the same budget. Known values remain available on partial rounds, but an unknown state is never written as a healthy zero.

Scrape /gpu-memory-metrics?target=<configured-alias> on the existing exporter listener. This is cache-only: calling it more often cannot poll the BMC. An unavailable/expired cache returns HTTP 503; incomplete available results explicitly publish gpu_memory_state_scrape_success=0. Preserve the existing gpu-memory-state job, BMC instance and host/GPU labels in the site scrape configuration. Set honor_labels: true or otherwise preserve exporter-provided BMC identity and use a unique target instance label for synthetic up metrics. If the monitoring client is not on the same network namespace as the loopback-bound exporter, use the existing authorized collection/relay path rather than changing the bind address.

The existing gpu_memory_state_* event, flag, coverage and observation metrics retain their names. State uses the Python v1 address/GPU and UUID|serial baseline format, with an optional per-counter source timestamp. First observations and changed GPU identity establish a baseline, not an event; a low segment needs three independent observations, with buffered growth and a 600-second maximum observation gap. Historical rebound (e.g. 9 → 0 → 9) and reset-marker changes signal discontinuity instead of replaying historical counts. New events are exposed only after durable state save.

Before adopting:

1. Save a private copy of the original Python baseline. Give Rust a private copy, not the same live file. Never let two processes write the same baseline.
2. Replay normal growth, history rebound, reset marker, replaced GPU, old report, partial reads and restart. Verify the exact BMC/GPU identities, four counters, Pending/Failed and completeness at the real scrape cadence. Do not read a counter replay from a dashboard as fresh device evidence.
3. Use an isolated test target, then compare cached output and alert evaluation. Keep existing alert rules until equivalence is proven. Do not turn on a second overlapping poller on the same fleet as a routine validation method.
4. Schedule site cutover separately. Before withdrawing the old monitoring input, verify cache readiness, sample freshness and coverage. Roll back to the saved Python baseline and original scrape if the new collector cannot keep up. A repository release is not a site deployment.
